# Лабораторная работа №2 — архитектура и пояснения

## Цель работы

Развить сервис агроскоринга из лабораторной №1: обеспечить сквозную идентификацию HTTP-запросов, асинхронное устойчивое хранение, пакетный inference, ограничение нагрузки и LLM-пояснения без вмешательства в детерминированный расчёт риска.

## Архитектура

```text
HTTP client
   │  X-Request-ID
   ▼
FastAPI middleware ──► structured logs + X-Process-Time
   │
   ├── /predict ───────────────┐
   ├── /batch-predict ─────────┼──► inference.py (общий asyncio.Lock)
   └── /predict-queued ─► Queue/worker ┘          │
                                                   ▼
                                           model.calculate_risk
                                                   │
                                                   ▼
                                        repository.py / aiosqlite
                                                   │
                                                   ▼
                                          SQLite (WAL, predictions)

/llm/chat ───────────────► lifespan-owned httpx.AsyncClient ─► Vireonix
/predict-with-llm ─► deterministic scoring → SQLite → Vireonix explanation
```

### Роли модулей

- `main.py` — сборка приложения, lifespan, маршруты и middleware.
- `errors.py` — единый error body с `request_id`.
- `schemas.py` — входные и выходные Pydantic-модели.
- `services.py` — проверки регионов, risk level и recommendation.
- `model.py` — неизменённая математическая функция `calculate_risk`.
- `inference.py` — общая точка single/explicit/dynamic inference и один lock на event loop.
- `batching.py` — ограниченная очередь, накопление до 8 элементов или 50 мс, worker и futures.
- `database.py` / `repository.py` — WAL, асинхронные parameterized SQL-запросы, транзакции.
- `llm_client.py` — OpenAI-совместимый HTTP-пayload, timeout и проверка ответа Vireonix.

## Теоретические вопросы

### Почему `sqlite3.execute()` нежелателен внутри async endpoint?

`sqlite3` синхронен: во время обращения к диску он блокирует поток event loop. Пока выполняется запрос, другие coroutine не получают управление, растёт latency и снижается пропускная способность. `aiosqlite` переносит блокирующую часть в выделенный поток и предоставляет awaitable API, поэтому endpoint отдаёт управление event loop на `await`.

### Почему `executemany()` с одним `commit()` лучше отдельных INSERT и COMMIT?

Один batch уменьшает число переключений и fsync/транзакционных накладных расходов. Главное — атомарность: при ошибке весь batch откатывается, а клиент не получает частично сохранённые результаты. В `save_predictions_batch` используется `executemany()`, затем один `commit()`; ошибка ведёт к `rollback()`.

### Что происходит при неограниченной очереди?

При входной скорости выше скорости модели заявки бесконечно накапливаются. Память процесса растёт, время ожидания каждой новой заявки увеличивается, после чего сервис может исчерпать память и стать недоступным. Ограничение `QUEUE_MAX_SIZE=100` создаёт backpressure: вместо накопления endpoint возвращает 429 и `Retry-After`.

## Роль основных механизмов

- **request_id** связывает входящий запрос, headers, логи, строки SQLite и LLM-вызов; это основа трассировки и расследования ошибок.
- **explicit batching** позволяет клиенту передать до 8 объектов и выполнить одно обращение модели и одну транзакцию хранения.
- **dynamic batching** объединяет конкурентные `/predict-queued` за окно 50 мс, сохраняя соответствие каждого `Future` своему запросу.
- **backpressure и timeout** ограничивают очередь и время ожидания, превращая перегрузку в контролируемые 429/504 вместо деградации сервиса.
- **SQLite** даёт переживающую перезапуск историю, WAL и async I/O.
- **LLM** формирует только объяснение уже рассчитанного результата; в prompt не передаются farm ID, долг и другие лишние данные.

## Заключение

Детерминированная модель остаётся источником истины, а асинхронная инфраструктура делает API наблюдаемым и устойчивым. Реальная доступность Vireonix — внешняя переменная: код и mock-тесты проверены, но сетевой провайдер периодически возвращал 502, что отражено в тестовом отчёте.
